## 1. Контекст проекта

Вы работаете в команде данных маркетплейса. Платформа собирает данные о заказах, оплатах, доставке, товарах, поиске и пользовательских событиях. Бизнес хочет видеть оперативные метрики почти в реальном времени, а финансовая команда требует точной сверки денег на следующий день.

Вам нужно спроектировать и частично реализовать аналитический контур, который:

- принимает данные из разных источников;
- строит слои `raw`, `stage`, `core`, `mart`;
- считает витрины для BI;
- умеет переобрабатывать поздние события;

- выдерживает рост объема и сбои;
- содержит читаемый и тестируемый код.

Основной домен проекта — заказы, оплаты, доставка, товарная аналитика и пользовательская воронка.

## 4. Бизнес-требования

### 4.1 Операционный BI

Операционные отчеты нужны менеджерам маркетплейса в течение дня.

Требования:

- задержка обновления витрин: не более **15 минут**;
- данные могут быть предварительными;
- допускаются корректировки задним числом;
- обязательно показывать `data_loaded_at` и `event_date`;
- при проблеме качества данных витрина должна иметь статус надежности.

### 4.2 Финансовый контур

Финансовая отчетность должна быть точной и сверенной.

Требования:

- публикация финансовых витрин: **D+1**;
- обязательная сверка заказов, оплат, возвратов и chargeback;
- период должен закрываться через `freeze`;
- исправления после закрытия периода — только через correction events;
- все изменения должны быть аудируемыми.

### 4.3 История и объемы

- хранить историю минимум **3 года**;
- данные событий приложения могут быть очень большими;
- события могут приходить с задержкой;
- источники могут менять схему;
- часть данных содержит PII.

### 12.5 Сверка сумм

```sql
SELECT
    o.dt,
    SUM(o.paid_amount) AS orders_paid_amount,
    SUM(p.success_payment_amount) AS payments_amount,
    SUM(o.paid_amount) - SUM(p.success_payment_amount) AS diff
FROM mart_orders_daily o
JOIN mart_payments_daily p ON p.dt = o.dt
GROUP BY o.dt
HAVING ABS(SUM(o.paid_amount) - SUM(p.success_payment_amount)) > 0.01;
```

- SQL-запросы корректны по гранулярности;
- агрегации не ломаются после `JOIN`;
- late events учтены;
- есть проверки качества данных;
- Python-код покрыт тестами;
- рефакторинг устраняет исходные проблемы;
- студент может объяснить сложность решений;
- README позволяет запустить проект локально.

## 17. Частые ошибки

- считать деньги после many-to-many `JOIN`;
- использовать `loaded_at` вместо `event_ts` для пользовательских метрик;
- считать `COUNT(*)` там, где нужен `COUNT(DISTINCT user_id)`;
- не учитывать возвраты и отмены;
- смешивать операционные и финансовые SLA;
- делать backfill в том же контуре, что и ежедневный отчет;
- хранить PII в витринах;
- писать один огромный SQL без этапов;
- не проверять row count и суммы после трансформаций;
- не указывать grain таблицы.
